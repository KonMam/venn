# Performance

Numbers for venn on its own, and for the same workloads run through other
tools. Everything here comes from `bench/run_bench.py`, which is documented
in [../bench/README.md](../bench/README.md) and reproducible.

## Method

One machine, an M1 Pro laptop with 16 GB, macOS, warm cache. Same fixtures
for every tool, generated by `internal/fixture` with the ground truth in
`manifest.json`.

1. **Correctness gate.** Every tool runs the case once and its
   added/removed/changed counts have to match the manifest exactly. A tool
   that answers wrong is not timed for that case.
2. **Timing.** hyperfine on a warm cache, reporting its mean. Runs are
   tiered by how long the case takes: 10 runs after 2 warmups under 20 s,
   3 runs after 1 warmup over 20 s, 2 runs over 60 s, where run-to-run
   variance on a multi-minute command is a few percent anyway.
3. **Memory.** One `/usr/bin/time -l` run per tool, peak RSS.

Tool and library versions for the published numbers are pinned in
[../bench/versions.lock](../bench/versions.lock). Every workload computes
both the row counts and per-column attribution, so each tool is doing the
same amount of work.

```bash
python bench/run_bench.py --help
```

## venn

| Workload | Wall | Peak RSS |
|---|---:|---:|
| 10M×15 parquet vs parquet | 1.1 s | 0.7 GB |
| 10M×15 csv vs csv | 2.5 s | 0.5 GB |
| 10M×15 csv.gz | 7.5 s | 0.2 GB |
| 100M×15 parquet | 17.2 s | 0.9 GB |
| 1B×5 parquet (70 GB/side) | 124 s | 1.1 GB |

Memory is a function of the batch engine rather than of the input, so the
1B-row diff peaks near where the 10M-row one does. `--summary` is one scan
instead of two: the 1B diff drops to 61 s, csv.gz to 3.8 s.

## DuckDB SQL

The same diff written as `FULL OUTER JOIN … IS DISTINCT FROM`, plus a second
query for per-column attribution. The generator for the queries is
[../bench/competitors/gen_duckdb_sql.py](../bench/competitors/gen_duckdb_sql.py).
DuckDB 1.4.3, default settings, same machine:

| Workload | venn | DuckDB SQL |
|---|---:|---:|
| 10M×15 parquet vs parquet | 1.1 s / 0.7 GB | 1.3 s / 1.7 GB |
| 10M×15 csv vs csv | 2.5 s / 0.5 GB | 3.9 s / 1.9 GB |
| 10M×15 csv.gz | 7.5 s / 0.2 GB | 12.1 s / 2.0 GB |
| 100M×15 parquet | 17.2 s / 0.9 GB | 129 s / 6.4 GB, swapping |
| 1B×5 parquet (70 GB/side) | 124 s / 1.1 GB | not attempted on 16 GB |

The two are close at 10M and diverge once the join no longer fits in memory.
DuckDB is a database doing a general-purpose join; venn only ever does this
one operation, which is what buys the bounded memory. On a larger machine, or
with data already loaded into a warehouse, the picture changes in DuckDB's
favour — see the note at the end of
[What it's for](../README.md#what-its-for).

`bench/competitors/` also holds the pandas and datacompy runners the harness
measures against. They are in the matrix at the smaller sizes; the numbers
are not published here yet.

## What the timings leave out

Timing one query against one command hides the work around it. venn also
gives you per-column attribution and example rows without a second unpivot
query, exit codes and `--max-diff` budgets, differing rows exported as data,
key inference, duplicate-key handling, dirty-CSV recovery, snapshot pruning,
and merge-on-read semantics. Weigh that alongside the table rather than
reading the table alone.
