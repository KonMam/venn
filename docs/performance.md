# Performance

Everything here is measured by `bench/run_bench.py`, the competitor harness
described in [../bench/README.md](../bench/README.md).

## Method

One machine, an M1 Pro laptop with 16 GB, macOS, warm cache. Every tool gets
the same fixtures, generated by `internal/fixture` with the ground truth in
`manifest.json`, and every workload computes the row counts and per-column
attribution.

1. **Correctness gate.** Each tool runs the case once and its
   added/removed/changed counts have to match the manifest exactly. A tool
   that answers wrong is not timed for that case.
2. **Timing.** hyperfine, mean of a run count tiered by case duration: 10
   runs after 2 warmups below 20 s, 3 runs after 1 warmup above it, 2 runs
   above 60 s.
3. **Memory.** One `/usr/bin/time -l` run per tool, peak RSS.

Tool and library versions behind the published numbers are pinned in
[../bench/versions.lock](../bench/versions.lock).

## venn

| Workload | Wall | Peak RSS |
|---|---:|---:|
| 10M×15 parquet vs parquet | 1.1 s | 0.7 GB |
| 10M×15 csv vs csv | 2.5 s | 0.5 GB |
| 10M×15 csv.gz | 7.5 s | 0.2 GB |
| 100M×15 parquet | 17.2 s | 0.9 GB |
| 1B×5 parquet (70 GB/side) | 124 s | 1.1 GB |

The batch engine keeps a bounded number of rows in flight whatever the input
size, so the 1B-row diff peaks at roughly the footprint of the 10M-row one.
`--summary` is one scan instead of two: the 1B diff drops to 61 s, csv.gz to
3.8 s.

## DuckDB SQL

The same diff as a `FULL OUTER JOIN … IS DISTINCT FROM` query, with a second
query for per-column attribution, generated by
[../bench/competitors/gen_duckdb_sql.py](../bench/competitors/gen_duckdb_sql.py).
DuckDB 1.4.3 on default settings, same machine and same fixtures:

| Workload | venn | DuckDB SQL |
|---|---:|---:|
| 10M×15 parquet vs parquet | 1.1 s / 0.7 GB | 1.3 s / 1.7 GB |
| 10M×15 csv vs csv | 2.5 s / 0.5 GB | 3.9 s / 1.9 GB |
| 10M×15 csv.gz | 7.5 s / 0.2 GB | 12.1 s / 2.0 GB |
| 100M×15 parquet | 17.2 s / 0.9 GB | 129 s / 6.4 GB, swapping |
| 1B×5 parquet (70 GB/side) | 124 s / 1.1 GB | not attempted on 16 GB |

At 10M rows the two are within 20% on parquet and about 1.5x apart on csv.
At 100M the join stops fitting in 16 GB and DuckDB spills, which is where
the rest of the gap comes from. A general-purpose join has to keep both
sides addressable; venn computes this one diff, so it streams both sides
against a fixed memory budget.

These numbers are one laptop. More RAM, or data already loaded into a
warehouse rather than read from parquet on disk, moves them toward DuckDB.

The measured workload is counts plus attribution only. Exit codes,
`--max-diff` budgets, exported diff rows, key inference, duplicate-key
handling and merge-on-read semantics are not part of it.

pandas and datacompy runners live in `bench/competitors/` and run in the
matrix at the smaller sizes. Those numbers are not published yet.
